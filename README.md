# 工数予測システム(第1版)

`工数予測システム_設計書.md` の実装。
実装範囲は設計書 9章「実装順序」の **1〜2(素朴版 + マイルストーン位置合わせ)**。

過去プロジェクトの月次実績から学習し、契約人月と期間が決まっている未来プロジェクトの
**月 × 行程グループ の工数配分**を予測して Excel に出力する。

---

## 1. すぐ動かす

```bash
pip install -r requirements.txt
python main.py
```

`output/forecast_PJ-2026-K_align-on_行程グループ.xlsx` が出力される。

サンプルデータを作り直したい場合:

```bash
python scripts/generate_sample_data.py
```

後から HTML 出力を足す際も計算部には手を入れない。

## 3. コマンドライン

**引数は `master.xlsx` の `settings` シートへの上書き**として働く。
繰り返し使う設定はシートに書いておき、その場だけ変えたいときに引数を渡す、という使い分けになる。
指定できる設定の全体像は [`settings` シート ─ 設定の一覧](#settings-シート--設定の一覧)を参照。

| オプション | 説明 |
|---|---|
| `--target PJ-2026-K` | 予測対象の案件ID。`,` または `;` 区切りで複数指定できる。**省略時は `ステータス=予測対象` の案件をすべて出力** |
| `--align on/off` | マイルストーン位置合わせの有無。省略時は settings の値 |
| `--group-col 大分類` | 学習粒度の切り替え。`phase_map` の列名を指定する |
| `--n-bin 200` | 正準時間軸の分割数 |
| `--backbone "α版;β版"` | 位置合わせに使うマイルストーンを明示指定 |
| `--backbone-coverage 0.6` | 背骨に採用する最小カバー率(0〜1)。1.0 で「全案件必須」 |
| `--ms-precision 月/自動` | マイルストーン日付の精度。既定 `月` は月央に丸める。`自動` は日まで書いた精度をそのまま使う |
| `--warp-strength 0.7` | 位置合わせの強さ(0〜1)。下げると工数の跳ねが小さくなる |
| `--max-stretch 1.5` | 時間軸の伸縮率の上限(倍)。跳ねの高さに直接上限をかける |
| `--exclude-group "サウンド;PM・運営"` | この案件が行わない行程グループを予測から外す |
| `--ignore-estimates` | `estimates` シートを使わず、契約人月と学習比率だけで予測する |
| `--reconstruct box/smooth` | 月次から月内分布を復元する方式。`box`=月内均等(既定) / `smooth`=累積の単調補間 |
| `--no-compare-recon` | 検証で復元方式を比較しない(既定は両方式を並べて出す) |
| `--phased auto/on/off` | 段階予測(マイルストーンごとに実績を確定させ、残りを予測)。既定 `auto` は実績とマイルストーンがある案件で自動出力 |
| `--interval-elasticity 0.5` | 学習データより狭く潰れた区間への工数配分を減らす(0〜1)。マイルストーンの日付は動かない |
| `--actuals path/to/actuals.csv` | 実績CSVの場所。省略時はマスタと同じフォルダの `actuals.csv` |
| `--remain-basis fixed/scaled` | 段階予測の残工数の決め方。`fixed`=契約・見積もりの総量を固定(既定) / `scaled`=確定分の実績から総量を引き直す |
| `--ramp-limit 自動/1.3/off` | 月次工数の増加率の上限(前月比)。既定 `自動` は実績の前月比90%点から決める |
| `--ramp-scope phased/all/off` | 上限をどこに効かせるか。`phased`=段階予測のみ(既定) / `all`=全期間予測と検証にも / `off`=使わない |
| `--no-validate` | leave-one-out を省略(高速) |
| `--phased-milestones すべて/通過済み` | 段階予測でマイルストーンをどこまで既知とするか。既定 `すべて` |
| `--out path.xlsx` | 出力先を指定(予測対象が1件のときだけ) |
| `--out-dir dir/` | 出力先ディレクトリ。既定は `output/` |

**予測対象が複数あれば、1回の実行で全部出力する。** 読み込み・集約・leave-one-out の
検証は案件に依存しないので1回だけ行う。

**学習は案件ごとにやり直す。** 予測対象が完了案件のときは、その案件を学習から外す
(自分の実績で学習したカーブで自分を予測しないため)。まとめて外して1回だけ学習する
ほうが速いが、それだと対象の数だけ学習データが減るため、1件ずつ外している。

1件が不備で落ちても、残りの案件は出力される。

出力ファイル名は**案件の名称**と条件でできている
(`シャドウヴェイル_align-on_行程グループ.xlsx`)。関係者に渡すのは名称であって
案件IDではないため、受け取った側がどの案件か分かる形にしてある。
名称が同じ案件が複数ある場合だけ、案件IDを添えて区別する。
パラメータを変えて実行すれば、条件違いのファイルが並んで比較できる。

```bash
# 位置合わせの有無を比較する
python main.py --align on
python main.py --align off

# 予測対象を明示して複数まとめて出す
python main.py --target PJ-2026-K,PJ-2027-L

# 粒度を粗くして当たりやすさを見る
python main.py --group-col 大分類

# 完了案件で「途中まで確定 → 残りを予測」が当たるかを見る
python main.py --target PJ-2021-E
python main.py --target PJ-2021-E --remain-basis scaled

# 全完了案件で段階予測の精度をまとめて測る
python scripts/evaluate_phased.py
```

## 4. 入力データ

### `data/master.xlsx`

| シート | 列 |
|---|---|
| `projects` | 案件ID / 名称 / 種別 / 契約人月 / 開始 / 終了 / ステータス **+ マイルストーン列** |
| `estimates` | 案件ID / 行程グループ / 見積人月 |
| `phase_map` | 実績行程名 / 標準行程名 / 行程グループ / 大分類 |
| `settings` | 区分 / パラメータ / 値 / 説明。**動作を変える設定はすべてここに並ぶ**(下の一覧) |

- 青字のセルが手入力項目。各シート末尾に凡例がある
- 凡例はデータ本体と空行で区切られており、読み込み時に自動で切り捨てられる
- `ステータス=予測対象` の案件が予測対象になる。実績CSVに行が無くてよい
- `phase_map` は列を増やしてよい。`settings` の `集約軸` をその列名にすると学習粒度が変わる

#### `projects` シート ─ マイルストーンは案件情報の右に列として書く

固定列(案件ID / 名称 / 種別 / 契約人月 / 開始 / 終了 / タグ / ステータス)の**右側に
マイルストーンを列として並べ、見出し行をマイルストーン名にする**。

| 案件ID | … | ステータス | プロトタイプ | α版 | β版 | マスターアップ |
|---|---|---|---|---|---|---|
| PJ-01 | … | 完了 | 2019-11 | 2020-07 | 2021-08 | 2022-01 |
| PJ-02 | … | 完了 | | 2020-08 | 2020-11 | 2021-01 |

- 日付は **`2020-08` と月まででよい**(開始・終了と同じ粒度)。`2020-08-22` と日まで書いてもよいが、
  既定では月精度に丸めて扱う(次節)
- **マイルストーン名は見出し行で1回決まる**ので、案件ごとの表記の揺れが起きない
- **空欄 = 未記入**。どの案件に何が入っているかがシートを見るだけで分かる
- 案件1行を書けば入力が終わる。シート間を往復しない
- マイルストーンが1件も無い案件・列が1つも無いマスタでも動作する(設計書 3-2)
- 日付が1つも入っていない列はマイルストーン列として読まないので、メモ欄を足してよい

旧形式(`milestones` シートに 案件ID / マイルストーン名 / 日付 の3列)も引き続き読める。
既存のマスタは移行スクリプトで変換できる。

```
python scripts/migrate_master_wide.py --master data/master.xlsx
```

変換前のファイルは `<名前>.bak.xlsx` として残り、旧シートは `milestones_旧` に改名される。

#### 月まで書くか、日まで書くか

`2020-08`(月まで)と `2020-08-22`(日まで)のどちらでも書ける。混在してよい。
月表記は `2020/8` `2020年8月` の形でも読める。

**月表記はその月の「中央」として扱う。** 月初として扱うと、実際の日付が月内に
散っているぶんだけ全案件のマイルストーンが半月ぶん前へ寄る。同じ向きにずれるので、
これは案件数を増やしても消えない系統誤差になる。

完了30件で、日まで書いた場合と月に丸めた場合を比べた実測(月次誤差WAPE):

| 日付の粒度 | 平均 | 中央 | 最悪 |
|---|---|---|---|
| 日まで | **0.2898** | 0.3049 | 0.4728 |
| 月まで(月央として扱う) | 0.3008 | 0.3121 | 0.5019 |
| 月まで(月初として扱う) | 0.3245 | 0.3416 | 0.5454 |
| 月まで(月末として扱う) | 0.3130 | 0.3332 | 0.5070 |

- **日まで書くと平均で 0.011 良くなる(相対 4%)。** ただし案件ごとに見ると
  月央のほうが良かった案件が 30件中13件あり、差の 95%信頼区間は −0.001〜+0.023 で
  0 をまたぐ(t = 1.84)。**はっきりした差とは言えない**
- 一方、**月初として扱うと 0.035 悪化する(相対 12%)。** これは日と月の差より大きい

**そこで既定は「すべて月精度」にしてある**(`settings` の `マイルストーン精度 = 月`)。
実績が月単位である以上、日まで分かっても得るものは小さく、
月初へ寄る事故のほうが害が大きいため。

| 値 | 動き |
|---|---|
| `月`(既定) | すべてのマイルストーンを月精度とみなし、月央へ丸める |
| `自動` | `2020-08` のような月表記だけ月央として扱い、日付は書いた精度のまま使う |

```
python main.py                    # 既定。月精度で揃える
python main.py --ms-precision 自動  # 日まで書いた日付をその精度のまま使う
```

既定を `月` にしている理由はもう一つある。セルに `2020-08` と入力すると、
Excel が 2020-08-01 という**日付**に変換してしまうことがある。こうなると
読み込み側では月表記と区別がつかず、上の表の「月初として扱う」状態
(相対 12% 悪化)のまま気づけない。既定が `月` ならこの事故が起きない。

日付が正確に分かっていてその精度を使いたい場合だけ `自動` にすること。
その場合は Excel のセルが `2020-08-01` のように1日ばかりになっていないか
必ず確認する(なっていれば、それは月表記が日付化されたものなので `月` に戻す)。

`月` では、同じ月に入った複数回のマイルストーンは1件にまとまる
(手戻り期間が1ヶ月未満だった分は区別できない)。警告に件数が出る。

入力の手間をかけるなら、日を細かくするより**記入する案件を増やすほうが効く**
(マイルストーンの記入率はカバー率を通じて背骨の選定に直接効く)。

#### 同じマイルストーンが複数回あるとき

マイルストーンは「このまま進めてよいか」を判断する機会でもあるので、
通過できずにやり直し、同じ名前のマイルストーンが2回・3回と訪れることがある。
その場合は**同じセルにカンマ区切りで日付を並べる**。列は増やさない。

| 案件ID | … | α版 | β版 |
|---|---|---|---|
| PJ-01 | … | `2020-04, 2020-08` | 2021-01 |
| PJ-02 | … | `2021-03-05` | 2021-11-02 |

区切りはカンマ・読点(、)・セミコロン・改行のいずれでもよい。
日付は `2020/4` `2020年4月` `2020/4/18` のどの形でも読める
(スラッシュは日付の一部なので区切りには使えない)。

読み込み時に、意味で切り分ける。

| | 扱い |
|---|---|
| **最終回** | `α版` = その工程を実際に抜けた日。**工程の境目はここ**で、位置合わせのアンカーになる |
| **初回** | `α版(初回)` という別のマイルストーンを自動で作る。レビューに入った日 |
| 中間 | アンカーとしては使わない(3回目の中間は位置の意味が定まらない) |

アンカーは案件ごとに1つの名前につき1点でなければならない(2点あるとワープが
一対一でなくなり、逆変換が壊れる)ため、この切り分けが要る。
初回〜最終回の間隔がそのまま**手戻り期間**になる。

##### ノイズにならないか ─ 完了30件(うちやり直しあり14件)での実測

**現在の扱いではノイズになっていない。**

**① やり直し案件を学習に混ぜても、他の案件の予測は悪くならない**
(やり直しの無い16件を予測。月次誤差WAPE)

| 学習データ | 平均 | 最悪 |
|---|---|---|
| やり直し案件を外す(15件) | 0.309 | 0.500 |
| やり直し案件も使う(29件) | 0.315 | 0.502 |

学習件数がほぼ倍になっても平均はほぼ変わらない(+0.006)。
つまり**やり直し案件から得るものは少ないが、害も無い**。除外する理由は無い。

**② アンカーは最終回にするのが正しい**(やり直しのあった14件を予測)

| アンカーの決め方 | 平均 | 最悪 |
|---|---|---|
| **最終回(現在の扱い)** | **0.285** | 0.441 |
| 初回 | 0.377 | 0.590 |
| α版を位置合わせに使わない | 0.351 | 0.471 |

「複数回あるから α版 は使わない」より、最終回を使うほうが 19% 良い。

**③ 平均位置はほとんど動かない**

| 学習データ | α版 | β版 | マスターアップ |
|---|---|---|---|
| 全案件 | 0.485 | 0.741 | 0.918 |
| やり直しなしだけ | 0.460 | 0.748 | 0.919 |

やり直し案件は α版 が遅め(位置 0.515 対 0.460)なので平均は後ろへ動くが、
その差 +0.025 は α版 位置の標準偏差 0.075 の3分の1にとどまる。

ノイズにならない理由は3つ。

1. 複数の日付が `α版` と `α版(初回)` に**分解される**ので、同じ名前で2点が競合しない
2. `α版(初回)` はやり直しのあった案件しか持たないため、既定のカバー率 0.6 では
   **背骨に選ばれない**。時間軸を決める部分には触らない
3. 手戻り期間の工数は、学習カーブでは α版 直前の質量として吸収される
   (s=0.20〜0.55 の質量が 0.397 → 0.426)。カーブ全体の差は総変動距離 0.104 と小さい

##### ノイズになる条件

- **`背骨マイルストーン` を明示指定すると `α版(初回)` も背骨に入りうる。**
  明示指定はカバー率を無視し、2案件あれば採用するため。
  入れるとやり直しのあった案件の WAPE が 0.273 → 0.344 と悪化した
  (位置合わせ強度 0.7、伸縮率上限 1.5 のどちらでも同じ方向)。
  母数が少なくアンカーが不安定なうえ、`α版` のすぐ手前に来るため区間が細くなり、
  時間軸の伸縮率が跳ねる(「位置合わせの強さ」の節の跳ねと同じ構造)。
  **`背骨マイルストーン` は `自動` のままにするか、指定するなら `(初回)` を含めないこと。**
- やり直し案件の比率がもっと高く、手戻り期間が長いと、`α版` の平均位置が
  やり直し側へ引っ張られる。今回は 14/30 で +0.025 だったが、比率が上がれば効く。
  `scripts/diagnose_warp.py` が出す各マイルストーンの標準偏差で確認できる。
- 中間回(3回中の2回目)は捨てているので、その情報は使っていない。

やり直しの回数そのものは記録として残り、警告に出る。

#### `estimates` シート ─ 着手前の案件に、要素別の見積もりを入れる

これから着手する案件は実績が1行も無く、分かっているのは**要素別の見積もりだけ**になる。
その入力口が `estimates` シート(設計書 6 Step1 の「制約の階層」)。

| 入力 | グループ別の総量 | 総工数 |
|---|---|---|
| 見積もり **なし** | 契約人月を学習した工数比率で配分 | 契約人月 × 換算係数 |
| 見積もり **あり** | 見積人月をそのまま使う | 見積人月の合計 |

```
案件ID       行程グループ    見積人月
PJ-2026-K   企画・プリプロ      130
PJ-2026-K   プログラム         620
PJ-2026-K   アート            700
```

- **書かなかった行程グループは「この案件では行わない業務」として予測から除外される**。
  サウンドは全編外注、ローカライズ無し、といった案件差をここで表現する
- 見積もりを入れない案件はシートに行を書かなければよい。1行も無ければ従来どおり動く
- 見積もり合計が契約人月とずれる場合は、**見積もり側を総量として採用**し、
  差を `予測` シートの注記に出す。どちらが正かは人が判断すること
- 見積もりが無い段階で列だけ落としたいときは `--exclude-group` を使う
  (この場合は総工数を動かさず、残ったグループへ学習比率のまま配分し直す)

#### `settings` シート ─ 設定の一覧

**動作を変える設定はここから全部いじれる。**
コマンドライン引数はこのシートへの上書きとして働くので、引数を渡さなければシートの値で動く。

### `data/actuals.csv`

`案件ID / 行程 / メンバー / 所属 / チーム / 月 / 時間`

- 22,181 行。`dtype=category` で読み、parquet にキャッシュする(`data/.cache/`)
- `phase_map` に無い行程は**分析対象から除外する**。除外した行数・人月・行程名は警告に残る
- `メンバー / 所属 / チーム` は欠損してよい。主軸の予測は行程と時間だけで成立する(設計書 3-3)

### 制約は「必須」ではなく「あれば効く」(設計書 3-2)

- `milestones` シートが空でも動く。位置合わせが無効になるだけ
- マイルストーンが一部の案件にしか無くてもよい。全案件に共通するものだけが「背骨」に選ばれる
- 予測対象案件のマイルストーンは、指定した点だけが実測値として固定され、
  残りは学習した位置分布で内挿される

### 対象外データの扱い(重要)

実績CSVは機械が出力する前提なので、対象外のデータが混ざる。
**マスタに載っているものだけを使い、それ以外は集計前に落とす。**

| 落とすもの | 判定 | 落とす理由 |
|---|---|---|
| `phase_map` に無い行程 | 実績行程名の完全一致 | 対象外業務の工数が比率とカーブに混ざり、予測がその形に引っ張られる |
| `projects` に無い案件ID | 案件IDの完全一致 | 廃番・検証用・別部門のコードが混ざる前提 |
| 契約期間外の月の実績 | `projects` の 開始〜終了 | 端月に寄せると、元データに無い工数の山を最終月に作る |

いずれも**落とした量(行数・人月・該当名)を警告に出し、出力Excelの `条件` シートに残す**。
黙って捨てると総量が合わない原因を追えなくなるため。

対象に含めたいものがあれば、`phase_map` に行を追加するか `projects` の期間を直せばよい。
除外するより、マスタを直して学習データを増やすほうが有利。

**縮退の滑らかさ**(サンプルデータで実測)

| マイルストーンの整備状況 | 背骨 | 素朴版比の改善 |
|---|---|---|
| 全10案件にα版・β版・マスターアップあり | 3点 | **+69.7%** |
| 2案件で記録が欠損 | 3点(欠損案件は使わないだけ) | **+51.7%** |
| 全案件で記録なし | なし | **±0%**(素朴版と同一) |

背骨は「全案件に100%存在するもの」ではなく**カバー率の閾値**(既定 0.6)で選んでいる。
100%必須にすると、1案件の記録漏れだけで背骨が消え、他の9案件で稼げたはずの精度まで失う。
手入力データでは「存在しなかった」と「記録されていない」の区別がつかない(設計書 11章)ため、
この全か無かは実運用で頻発する。

### 消化カーブの形は1種類ではない

実データの消化カーブは「中央に大きな山が1つ」ばかりではない。
サンプルデータにも4つの型を混ぜてある(`scripts/generate_sample_data.py` の `PACE`)。

| 型 | 中身 |
|---|---|
| 標準 | 中央付近に山が1つ |
| 後半集中 | 前半は緩やかで、後半に一気に消化する |
| 前倒し | 早めに山が来て、終盤は落ち着く |
| 二山 | 山が2つに割れる |

マイルストーンの位置は動かさずに工数の置き場所だけを前後へ寄せてあるので、
**マイルストーンでは説明できない形のばらつき**がデータに残る。
これが無いと位置合わせの効果を過大評価してしまう。

`scripts/validate_patterns.py` は、実績から測った形(重心と山の数)で案件を分類し、
形ごとに leave-one-out の誤差を出す。分類は名称や種別ではなく実績そのものから
決めるので、実データでもそのまま使える。

```
python scripts/validate_patterns.py --master data_large/master.xlsx \
    --actuals data_large/actuals.csv
```

完了30件のサンプルでの実測(月次誤差WAPE、小さいほど良い):

| カーブの形 | 件数 | 素朴版 | 位置合わせ | 改善 |
|---|---|---|---|---|
| 後半集中型 | 10 | 0.426 | 0.299 | +0.127 |
| 標準型 | 9 | 0.307 | 0.216 | +0.091 |
| 二山型 | 5 | 0.447 | 0.339 | +0.107 |
| **前倒し型** | 6 | 0.471 | **0.399** | +0.071 |

| 期間 | 件数 | 素朴版 | 位置合わせ |
|---|---|---|---|
| 〜15ヶ月 | 2 | 0.337 | 0.189 |
| 16〜24ヶ月 | 9 | 0.373 | 0.267 |
| 25ヶ月〜 | 19 | 0.424 | 0.329 |

位置合わせはどの形でも改善するが、**前倒し型と長期案件が当てにくい**。
消化ペースを揃えた対照データでは位置合わせ後の WAPE が 0.12 まで下がるので、
残っている誤差のほとんどは「マイルストーンで説明できない形の差」である。
ここを縮めるには、マイルストーンを増やすか、種別・タグによる重み付け
(設計書 9 の実装順序 3・4)で似た形の案件を選んで学習する必要がある。

### 位置合わせの強さ(`--warp-strength` / `--max-stretch`)

位置合わせは時間軸を区間ごとに伸縮させる。工数密度は

    実時間軸の密度 = 正準時間軸のカーブ ÷ 伸縮率

なので、**伸縮率がアンカーの前後で k 倍変われば、その月に工数が k 倍跳ぶ**。
マイルストーン位置が学習データの平均から大きく外れた案件では、この跳ねが
実績には存在しない段差として月次グラフに出る。

| パラメータ | 既定 | 意味 |
|---|---|---|
| `位置合わせ強度` (`--warp-strength`) | 1.0 | 0〜1。実位置を正準位置へ引き戻す割合。1.0 = マイルストーン日付ちょうどに合わせる。0.0 = 位置合わせなし |
| `伸縮率上限` (`--max-stretch`) | 0(無制限) | 区間ごとの伸縮率を 1/k〜k 倍に収める。跳ねの高さに直接上限をかける |

既定値は従来の挙動と同じなので、指定しなければ結果は変わらない。
下げると跳ねは抑えられるが、カーブの山はマイルストーンちょうどには来なくなる。
**どちらが良いかはデータ次第**なので、採用する前に必ず診断すること。

```
python scripts/diagnose_warp.py --strengths 1.0 0.7 0.5 --max-stretch 1.5
```

案件ごとに「アンカー段差 / 密度倍率 / 跳ね度 / WAPE」を出し、設定値を並べて比較する。
**WAPE を悪化させずに跳ね度が下がる設定があれば採用する。** 無ければ位置合わせは
正しく効いているということなので、設定は変えない。

原因の詳細と実測値は [`docs/マイルストーン位置合わせの跳ね_調査メモ.md`](docs/マイルストーン位置合わせの跳ね_調査メモ.md)。

### 潰れた区間への配分(`--interval-elasticity`)

上の2つは時間軸を動かして跳ねを抑えるので、**マイルストーンの山が指定日付から
ずれる**。日付は信じたいが鋭さだけ抑えたい、という場合はこちらを使う。

区間が極端に狭いとき、案A(比率固定・期間のみ伸縮)は
「2ヶ月に全体の30%」のような**実在しない要員数**を要求する。
現実には、短い区間はたいてい判断のための版を作った区間で、工数そのものが軽い。
そこで**潰れた区間への配分だけを減らし、あふれた分を他の区間へ回す**。

| パラメータ | 既定 | 意味 |
|---|---|---|
| `区間弾力性` (`--interval-elasticity`) | 0 | 0〜1。学習データより狭く潰れた区間への配分を減らす度合い。1 で、区間が潰れたことによる密度上昇をちょうど打ち消す |

- **`0` が既定で、案Aと完全に一致する。** 指定しなければ結果は1セルも変わらない
- **マイルストーンの日付は動かない。** 変わるのは「どの区間にいくら置くか」だけ
- 区間の中の形は学習カーブのまま。追い込みのような区間内の山は残る
- 総工数と行程グループ別の総量も変わらない
- マイルストーンが学習データの平均どおりに並ぶ案件では、λ をいくつにしても何も起きない
- 学習側でも逆変換を通すので、学習カーブと予測が二重に補正されることはない

3つの抑え方の使い分け:

| | 抑え方 | マイルストーンの日付 |
|---|---|---|
| `位置合わせ強度` | 実位置を正準位置へ引き戻す | ずれる |
| `伸縮率上限` | 時間軸そのものを縮める | ずれる |
| `区間弾力性` | 区間への配分を減らす | **動かない** |

値は必ず実データで決めること。

```
python scripts/diagnose_warp.py --elasticity 0.3 0.5 0.8
```

**WAPE を悪化させずに跳ね度が下がる値があれば採用する。** 無ければ `0` のままにする ――
その跳ねは実態であり、消してはいけない。
区間弾力性は時間軸に触らないため `段差比` は変わらない。効果は `跳ね度` と `WAPE` に出る。

設計上の位置づけは設計書 3-1-2、実装は [`src/elasticity.py`](src/elasticity.py)。

### カーブ復元方式(`--reconstruct`)

月次工数から「月の内側の分布」をどう復元するかの選択。学習カーブの鋭さに効く。

| 方式 | 中身 | 性質 |
|---|---|---|
| `box` 月内均等(既定) | 月次工数を月の中に一様に撒く | 幅 1/月数 の箱型ぼかしと等価。期間の短い案件ほど山がなまる |
| `smooth` 単調補間 | 月境界の累積値を単調保存3次補間して微分 | 月内均等の仮定を外す。合計値は厳密に保存され、密度は負にならない |

合成データ(真値が既知)で測ると、単一案件のカーブ再現率は次のとおり。

| 案件期間 | 山の高さの再現率(box) | (smooth) |
|---|---|---|
| 4ヶ月 | 49.8% | 53.9% |
| 12ヶ月 | 87.9% | 103.6% |
| 36ヶ月 | 97.8% | 101.5% |

**ただし、実データで効くかは案件の期間構成による。**
既定は `box` のままにしてあるので、採用する前に leave-one-out で必ず比較すること。
`python main.py` を実行すると `検証` シートに両方式が並んで出る。

|---|---|---|---|
| 素朴版 | 0.262 | 0.095 | — |
| 位置合わせ(MS学習値) | 0.273 | 0.103 | **−4.4%** |
| 位置合わせ(MS指定) | 0.079 | 0.032 | **+69.7%** |

読み方:

- **位置合わせだけでは改善しない(むしろ微減)。**
  平均カーブを鋭くしても、その山を貼る位置が分からなければ意味がない。
  鋭い山を平均位置に置くと、実際の山とズレたときの誤差はかえって大きくなる。
- **対象案件のマイルストーン日付を与えると誤差が 1/3 になる。**
  これが設計書 5章 Step3 の「過去マイルストーンを手入力する価値は表示用ではなく
  カーブの解像度そのもの」という主張の裏付けにあたる数字。

実務上の含意は「マイルストーンは過去分も未来分も入力する価値がある」。
未来案件のマイルストーンが未定の場合、素朴版と大差ない精度になる点は認識しておく必要がある。

なお `カーブ` シートで、位置合わせありの平均カーブがα版・β版の位置に山を保っているのに対し、
位置合わせなしの平均カーブでは山がならされていることが目視できる。

## 7. 段階予測 ─ 途中まで実績が確定している場合の予測

着手前に全期間を予測するだけでは、**予測が当たっているかを案件が終わるまで判定できない**。
実運用で問われるのは常に「ここまでは実績で確定した。では残りはどうなるか」であり、
そこで初めて予測は意思決定に使われる。

`段階予測` シートは、その予測を**完了案件の上で再現**する。
マイルストーンを区切りに、そこまでの実績を確定値として置き、残りを学習カーブで予測する。

```
段階0  着手前          実績を一切使わず全期間を予測
段階1  プロトタイプ後     その日付が属する月までを実績で確定し、残り26ヶ月を予測
段階2  α版後          16ヶ月を確定し、残り20ヶ月を予測
段階3  β版後          27ヶ月を確定し、残り9ヶ月を予測
段階4  マスターアップ後    32ヶ月を確定し、残り4ヶ月を予測
```

完了案件なら全期間の実績が分かっているので、どの段階の予測がどれだけ当たったかを
案件の完了を待たずにそのまま数字にできる。グラフは実績1本(太い赤線)に
各段階の予測を重ねた折れ線で、月次と累積の2枚を出す。
確定分は実績そのものなので、各系列は確定した月までは実績の線と重なり、
**その先でどれだけ実績から離れるか**だけが予測の当たり外れになる。

### 評価するのは「まだ確定していない区間」だけ

確定分を混ぜて誤差を測ると、段階が進むほど自動的に数字が良くなる。
それでは予測が良くなったのか確定が増えただけなのか区別できない。
`段階予測` シートの誤差表は残り区間だけで測っている。

終盤の段階ほど残り区間は短く、量も小さい(最終段階は全体の数%しかない)。
誤差率はその小さい分母で割った値なので跳ねやすいため、
`残りが全体に占める割合` と併せて読むこと。

### マイルストーンをどこまで既知とするか(`--phased-milestones`)

**位置合わせは、対象案件のマイルストーン日付が与えられて初めて効く**(6章参照)。
段階予測でこれをどう扱うかで、グラフの形も精度も大きく変わる。

| 値 | 扱い | 意味 |
|---|---|---|
| `すべて`(既定) | 記入済みの日付を全部使う。`予測` シートと同じ条件 | 実運用では着手前から予定が引かれているので運用の実態に近い。ただし完了案件では記入値が実績の日付なので、**予定が完璧に当たった場合 = 精度の上限** |
| `通過済み` | その段階までに通過したものだけ | 未来を一切覗かない。ただし**予定を何も持たない場合 = 精度の下限**。背骨のマイルストーンを通過していない段階では位置合わせが効かず、素朴版と同じカーブになる |

実運用の精度はこの2つの間に入る。どちらか一方が正しいのではなく、
**上限と下限として両方を見る**のが正しい読み方になる。

```bash
python scripts/evaluate_phased.py --milestones compare
```

| 確定した期間 | すべて(上限) | 通過済み(下限) |
|---|---|---|
| 0%(着手前) | **0.286** | 0.357 |
| 〜25% | 0.274 | **0.262** |
| 〜50% | **0.234** | 0.307 |
| 〜75% | **0.233** | 0.262 |
| 75%超 | 0.393 | **0.383** |

`通過済み` では位置合わせが効いた段階が 67% にとどまる(`すべて` は 100%)。
シートの誤差表にある `位置合わせに使ったMS数` が 0 の段階は、
**位置合わせ ON でも素朴版と同じ形**になっている。

### 情報漏れの防止

段階予測は**対象案件を必ず学習から外した(leave-one-out)モデル**を使う。
自分の実績で学習したカーブで自分を予測しては評価にならない。
`予測` シートの本体は従来どおり全案件で学習しているので、
完了案件を対象にしたときは両者の数字が一致しない。これは意図的な差である。

マイルストーンの日付も同じ扱いで、**各段階で使うのは通過済みのものだけ**。
先のマイルストーンの実日付を渡すと未来を覗いた予測になる。
段階0 は通過済みが1つも無いので、日付を一切使わない。

### 残工数の決め方(`--remain-basis`)

| 値 | 決め方 | 効き方 |
|---|---|---|
| `fixed`(既定) | 総量は契約人月(または見積もり)のまま。残り = 総量 − 確定分 | 現場の運用に一番近い。総量の読み違いが**すべて終盤に溜まる** |
| `scaled` | 総量 = 確定分 ÷ 学習カーブの確定分比率。総量そのものを実績から引き直す | 契約人月が実態とずれている案件で効く。序盤は確定分が少なく不安定 |

行程グループごとに計算する。`scaled` で確定分の実績が 0 のグループは
引き直せないため契約・見積もりの値のままにし、その旨をシートに書く。

**総工数はどの段階でも動かない。** `fixed` の総量は契約人月(または見積もり)で
決まっており、実績を確定させても変わらない。`段階予測` シートの
`見込んだ総工数` 列が段階によって違う値になっていたら、それは配分のバグである
(実行時に検算していて、崩れれば止まる)。
唯一の例外は、確定分の実績が既に総量を超えている段階で、
実績を減らすことはできないため確定分そのものが下限になる。

### 立ち上がり制約 ― 人員は急には増やせない

前半の消化が低調だと、辻褄を合わせるために残り区間へ工数が上乗せされる。
このとき**残りのカーブを一律に縦へ伸ばすだけでは、山の位置は絶対に後ろへ動かない**。
遅れている案件では学習カーブの山が既に確定区間の中で終わっているため、
残りに貼るのは下り坂だけになり、**初月が最大値で以後は減る一方**という形が出ていた。

現実は逆で、人員は急に増やせないので山は後ろへ移動してなだらかになる。
そこで**月次工数の増加率に上限**を置き、あふれた工数を後ろの月へ送っている。

- 上限は**実績の前月比の90%点**から自動で決める(サンプルで1.33、大規模で1.39)。
  定数を決め打ちにすると実態と合っているか確かめられないため
- **総工数も行程グループ別の総量も動かさない。** 動かすのは「いつ消化するか」だけ
- 上限に当たらない段階では何も起きない

| 方式 | 境界段差 最大 | ピーク位置ズレ | 初月が最大 | 残り月次WAPE |
|---|---|---|---|---|
| 制約なし | 3.765 | −0.336 | 54% | 0.354 |
| **立ち上がり上限(既定)** | **1.396** | **−0.164** | **44%** | **0.350** |

**精度は悪化しない。** 形が現実的になるのと引き換えに精度を払う取引ではなかった。
詳細は `docs/確定直後の工数の跳ね_調査メモ.md`。

なお背骨位置合わせの突起(伸縮率がアンカーの前後で不連続に変わることによる尖り)にも
同じ制約が使えるが、**既定では効かせていない**。突起は減るが月次WAPE がわずかに悪化し、
サンプルデータでは突起が元々弱く判定できないため。`--ramp-scope all` で試せる。

### 切り替え点の段差(`残工数の倍率`)

確定分の実績が学習カーブの見込みより少ないと、
**総量を動かさない決まりのぶんだけ、そのずれが残り区間へ寄る**。
結果として切り替え点の直後に工数が段差として現れる。

`段階予測` シートの `残工数の倍率(学習カーブ比)` は
「残工数 ÷ 学習カーブが残り区間に置く量」で、**段差の高さそのもの**である。

| 倍率 | 意味 |
|---|---|
| 1.0 | 学習カーブどおり。段差は出ない |
| 1.0 より大 | 確定分が学習カーブより少ない。残りへ上乗せされ、切り替え点で**上へ**跳ねる |
| 1.0 より小 | 確定分が学習カーブより多い。残りが薄くなり、切り替え点で**下へ**落ちる |

倍率が 1.3 を外れた段階にはシートへ但し書きが出る。
これはバグではなく「この案件は学習した消化ペースから外れている」という診断であり、
段階予測が拾うべき情報そのものでもある。

### サンプルデータでの測定結果

`python scripts/evaluate_phased.py`(完了10件・位置合わせON)。
確定した期間の割合で束ねた、残り区間の月次誤差WAPE の平均。

| 確定した期間 | 契約総量固定 | 実績スケール | 残りが全体に占める割合 |
|---|---|---|---|
| 0%(着手前) | 0.286 | 0.286 | 100% |
| 〜25% | **0.274** | 0.639 | 83% |
| 〜50% | **0.234** | 0.794 | 72% |
| 〜75% | **0.233** | 0.662 | 46% |
| 75%超 | **0.393** | 1.087 | 8% |

読み方:

- **実績を確定させても、残り区間の精度は大きくは上がらない**(0.286 → 0.23〜0.39)。
  現在のモデルは「学習した形を期間に貼る」だけで、
  確定した実績の形をカーブの選択に反映していないため、これは当然の結果である。
  確定分が効いているのは総量の按分だけになっている。
- **`契約総量固定` がどの区間でも `実績スケール` より良い。**
  `実績スケール` は確定分1点からの外挿なので、
  そこに乗った案件固有のばらつきをそのまま総量に増幅してしまう。
  契約人月という外から与えられた情報のほうが、現状では強い。
- したがって現状の推奨は **`fixed`(既定)のまま**。`scaled` は
  契約人月が実態とずれていると分かっている案件で試す位置づけにとどめる。

**この数字はサンプルデータのものであり、実データでの結論ではない。**
サンプルは学習カーブと同じ発想で生成されているため、
実データより段階予測が有利にも不利にも振れうる(5章の注意書きと同じ)。
実データを入れたら `scripts/evaluate_phased.py` を回して測り直すこと。

### 残工数の決め方は、将来3パターンに増やす

知りたいことが違えば「残り」の正しい見込み方も違う。
**予定配分を守る / 総量を守って配分し直す / 総量を考慮せずこのまま進行する**の3本を
並べて見せる計画で、詳細と測定結果は設計書 14章にある。
現状出しているのは2番目に相当する1本だけである。

なお制約として、**見積もり全体は超過してはならないが、
グループ別の見積もりは超過・変化してよい**。現在の実装もこの前提で動いている。

### 精度を上げるとしたら

上の測定は「確定した実績を、残りの形の予測に使えていない」ことを示している。
次に試す価値があるのは次の2つで、どちらも段階予測の枠組みの上で効果を測れる。

1. **確定分の形に近い過去案件だけで学習する。** 確定区間の消化カーブが似ている案件に
   重みを寄せれば、「この案件は後半集中型だ」と途中で分かる。
   `learn(weights=...)` に重み辞書を渡す口が既に開いている(設計書 9章 実装順序3)。
2. **確定区間で総量の読み違いを検知する。** `実績スケール` はその最も素朴な形で、
   序盤に不安定なのは1点のみの外挿だからである。確定分の長さで
   `fixed` と `scaled` を混ぜる(信頼度で加重する)だけでも改善する余地がある。

## 9. うまくいかないときの切り分け

予測が不自然なとき、原因はほぼ予測ロジックではなくデータの取り込み側にある。
実行ログと `条件` シートの警告を先に読むこと。

| 症状 | 疑うところ |
|---|---|
| 期間の最後5%で工数が急上昇する | 契約期間外の実績。ログの「契約期間外に記録された実績を除外しました」を確認 |
| 特定の行程グループの比率が不自然 | `phase_map` に無い行程が大量に落ちていないか |
| 位置合わせが効かない(背骨が「なし」) | マイルストーンのカバー率が閾値未満。`--backbone-coverage 0.4` で緩められる |
| 消化率が t=0.5〜0.7 で100%に達する | 後半の工数が集計から欠落している。下記を順に確認 |

**消化率が途中で100%に達する場合**(再現実験で確認した候補)

| 原因 | 再現時の到達点 | 見分け方 |
|---|---|---|
| `終了` が実態より後ろ | — | 実績が実在する最終月と `終了` を比較する |
| 後半に偏る行程だけ命名規則が違う(`デバッグ(協力会社)` 等) | t=0.70 | 除外警告の行程名に `phase_map` と似た名前が無いか |
| 途中から月の書式が変わっている(`2022-07` と `2022/7`) | t=0.50 | 期間外として除外された行の `月` の値を見る |
| 後半の工数が別案件IDに付替(枝番・保守コード) | t=0.58 | 未登録IDの警告に、対象案件と似たIDが無いか |
| 中止・凍結された案件 | — | データの誤りではない。学習から外すべき案件 |

いずれも「後半の工数が集計から消える」型で、**元データを目視しても欠落は見えない**。
警告に出る除外量が切り分けの手がかりになる。

## 11. 動作環境

Python 3.10 以上。`pandas` / `numpy` / `openpyxl`。
parquet キャッシュを使う場合のみ `pyarrow`(無くても動作する)。
